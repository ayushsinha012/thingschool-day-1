Secret scan - Day 26
=====================

Scope: every file under day-26/ (source, infra, kql, evidence, README, result).

Searched for: connection strings with embedded keys (InstrumentationKey=,
AccountKey=, SharedAccessKey=, SharedAccessSignature=/sig=), passwords,
private key headers (BEGIN RSA/EC PRIVATE KEY), client secrets, JWT bearer
tokens, SAS tokens.

Command (representative):
  grep -rniE "InstrumentationKey=|password[:=][\"'][^\"' ]{4,}|AccountKey=|
    SharedAccessKey=|BEGIN (RSA|EC) PRIVATE KEY|client_secret|clientsecret"
    day-26 --include=*.cs --include=*.json --include=*.md --include=*.txt
    --include=*.bicep --include=*.kql

Result: one match, in evidence/app-insights.txt:
  connectionString: InstrumentationKey=<redacted>;IngestionEndpoint=...
This is the intentionally redacted placeholder documented in that file -
the real value was read into a process-local environment variable at run
time via `az monitor app-insights component show --query connectionString`
and was never written to any file in this repository.

Also checked separately: no raw JWT (`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9`
prefix), no `Bearer eyJ`, no Azure Storage/Service Bus SAS pattern
(`sig=`, `sv=20YY-`) anywhere under day-26/.

The one local secret this application needs at runtime - the local JWT
signing key (Jwt:Key) - was generated as a random 48-byte value and stored
only via `dotnet user-secrets` (outside the repository, under the user's
profile), scoped to a fresh UserSecretsId distinct from day-1's. It does
not appear in any Day 26 file.

The Application Insights connection string was resolved at process start
from `az monitor app-insights component show` directly into an environment
variable for that one process invocation - never written to appsettings.json,
launchSettings.json, or any other file.
